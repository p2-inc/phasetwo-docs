On Monday we [shipped the Management API](/blog/phasetwo-management-api) — 73 endpoints for
creating and configuring dedicated Keycloak clusters. Today, the declarative version.

```hcl
resource "phasetwo_cluster" "main" {
  name              = "acme-prod"
  region            = "US_EAST_1"
  tier              = "premium"
  organization_id   = data.phasetwo_organization.team.id
  payment_method_id = data.phasetwo_payment_method.default.id
}

resource "phasetwo_realm" "app" {
  cluster_id   = phasetwo_cluster.main.id
  name         = "app"
  display_name = "Acme Application"
}
```

`terraform apply`, wait a few minutes, and you have a dedicated Keycloak with a realm on it.

## Why bother, when there's an API

Because the interesting parts of cluster management are exactly the parts that are annoying to
write by hand, and the provider has already written them.

Provisioning is asynchronous — you have to poll for `ACTIVE`. Environment variable and extension
changes restart Keycloak, and the API rejects a second restart while one is in flight, so they
have to be serialized and waited on. Deletes are deferred to the end of the billing cycle.
Custom domains need DNS records you create in between two API calls.

Every one of those is a loop, a retry, or an ordering constraint in a shell script. In the
provider they are the provider's problem:

> **Environment variable and extension changes restart Keycloak.** The API rejects a second such
> change while one is in flight. The provider serializes them per cluster and waits for each
> restart, so a config with several works — but an apply that touches many will take as long as
> that many restarts.

That last clause is the honest trade. It is not free; it is just correct.

## Generated from the same spec

`internal/client` is generated by `oapi-codegen` from the same OpenAPI document that generates
the [API reference](https://phasetwo.io/api/management-api-index). When we add an endpoint, the
client regenerates; when we rename an operation, both move together.

On top of that sits a small hand-written layer for the things a generated client cannot know:
authentication, typed errors, and the restart serialization above.

## What it manages

| Resource                                  |                                                  |
| ----------------------------------------- | ------------------------------------------------ |
| `phasetwo_cluster`                        | A dedicated cluster                              |
| `phasetwo_realm`                          | A realm on a cluster                             |
| `phasetwo_cluster_domain`                 | A custom hostname, and the DNS records to create |
| `phasetwo_cluster_primary_host`           | Which domain the cluster serves on               |
| `phasetwo_cluster_ip_rules`               | Admin and realm IP allow/deny lists              |
| `phasetwo_cluster_environment_variable`   | A custom SPI variable                            |
| `phasetwo_cluster_extension` / `_version` | Custom providers and themes                      |

Plus data sources for organizations, payment methods, clusters, realms and regions.

Organizations and payment methods are **referenced, not managed**. Both involve flows that only
make sense in a browser — accepting terms, entering card details — so you create them in the
console and look them up:

```hcl
data "phasetwo_organization" "team" {
  name = "acme"
}

data "phasetwo_payment_method" "default" {
  organization_id = data.phasetwo_organization.team.id
  default         = true
}
```

## Credentials

Same API secret as the Management API, from the environment so it stays out of `.tf` files and
out of state:

```bash
export PHASETWO_CLIENT_ID='...'
export PHASETWO_CLIENT_SECRET='...'
```

The provider does the client-credentials exchange itself. There is also `PHASETWO_ACCESS_TOKEN`
if your CI already holds a token — the provider will use it and will not refresh it.

## Custom domains take two applies, on purpose

This is the one place the provider makes you do something in two steps, and it is worth
explaining rather than filing as a rough edge.

```hcl
resource "phasetwo_cluster_domain" "auth" {
  cluster_id = phasetwo_cluster.main.id
  host       = "auth.acme.com"
}

output "dns_records_to_create" {
  value = phasetwo_cluster_domain.auth.domain_records
}
```

Apply that, create the records it outputs at your DNS provider, and then in a second apply:

```hcl
resource "phasetwo_cluster_primary_host" "auth" {
  cluster_id = phasetwo_cluster.main.id
  host       = phasetwo_cluster_domain.auth.host
}
```

`wait_for_certificate` exists but defaults to **off**, because turning it on in the same apply
that produces the records you have not yet created would deadlock — the certificate waits on
DNS, and the DNS waits on you. If your DNS is itself in Terraform, set it with a `depends_on`
covering those records and it all happens in one pass.

## Read the plan on clusters

**Every argument on `phasetwo_cluster` forces replacement.** Not the tier, not the region — there
is no in-place cluster change. Replacing destroys the cluster and every realm on it.

Combined with deferred deletes, that has a consequence worth stating plainly: a cluster you
destroy keeps its name reserved until the billing cycle ends, so **recreating it under the same
name will fail**. In ephemeral environments, use distinct names.

Terraform tells you all of this in the plan. On this particular resource, read it.

## Where the provider stops

At the realm boundary. It creates realms; it does not create the clients, identity providers and
flows inside them. Hand off to a Keycloak provider pointed at the cluster it just built:

```hcl
provider "keycloak" {
  url       = phasetwo_cluster.main.host
  client_id = "admin-cli"
  # ...
}
```

Which mirrors the same split as the APIs themselves: `phasetwo_*` is the control plane, and
everything inside a realm is Keycloak's own API plus
[our extensions to it](https://phasetwo.io/api/extensions-api-index).

## Get it

```hcl
terraform {
  required_providers {
    phasetwo = {
      source  = "p2-inc/phasetwo"
      version = "~> 0.1"
    }
  }
}
```
